# Audit, November 2026

An audit of the whole codebase on 14–15 November 2026, at `145c36f`. Four passes read the
code in full: the Worker's security, the Worker's data logic, the front end, and the Study
area. A finding is listed here only if a test reproduced it; anything that could not be
shown by a test is under "Not confirmed" for its pass.

Each finding says where it is, what goes wrong, how to make it happen, and what was done.
"Fixed" means there is a regression test that failed before the change and passes now; the
test is named. "Open" means the code was left alone, with the reason: most of those need a
decision from George rather than a patch.

Severity: **high** loses or overwrites someone's data without telling them; **medium** is a
wrong result a person will meet in ordinary use, or a limit that can be got around; **low**
is a wrong word or number, or a hole that needs unusual effort to reach.

What is still open, as questions with a recommendation each and the tasks that follow, is
in `docs/superpowers/plans/2026-11-15-audit-follow-up.md`.

## Worker security

Regression tests: `test/audit-fixes.test.js`.

**S1. Medium. A project made with an impossible date broke every member's calendar feed.**
`worker/projects.js` `projectBody` checked a project's date only against the shape
`YYYY-MM-DD`. `POST /api/spaces {kind:'project', date:'2026-13-45'}` was accepted; from then
on the `.ics` feed of every member of that project answered `500` until the date was
rewritten. *Fixed:* the route now asks for a day that exists (`isDay` in `worker/time.js`,
which the item validator also uses), and the feed skips a stored row whose date is not a
real day, so one bad row cannot fail a whole feed. Tests: "a project needs a real date".
Worth a one-off check of the live database for `p:` items with such a date.

**S2. Medium. A Generate here run that returned no usable cards cost neurons that were
counted nowhere.** `worker/study-ai.js` gave the person's use back (as designed) and never
reached `recordUsage`, so neither the person's day nor the account's neuron ceiling moved:
ten such calls on a cap of three all ran the model. *Fixed:* the tokens a run reports are
kept as it goes, and a run that fails still adds its neurons to the day's total (it is not
counted as a generation), so the ceiling closes. The use is still given back, as the plan
and `test/study-ai.test.js` say. Tests: "Generate here counts what the model cost".
*Still open for a decision:* one person can now run the day's ceiling down for everyone
with answers that keep failing. A limit on give-backs per person per day would close that.

**S3. Low. Trusted-device cookies outlived a password reset.** The `rounds_device` cookie
was signed over the username alone, any number could be collected, and a new password or
Sign out everywhere retired none of them. Whoever once knew the password kept five guesses
per cookie and a way through a lock on the name. *Fixed:* the cookie is signed over the
name and the account's `pw_gen`, so a reset or Sign out everywhere retires them all. Cookies
issued before this change stop being trusted once; each browser gets a new one at its next
sign-in. Tests: "a trusted-device cookie ends with the password it was made under".

**S4. Low. An AI read that times out after a slow upload is handed back.** In
`worker/api.js` the 100-second deadline starts before the body is read, and `ai_timeout` is
in `GIVEN_BACK`: a read whose upload takes most of the deadline reaches the model, times
out and is not counted toward the ten a day. Shown with a simulated clock only; whether
Cloudflare delivers an upload that slowly was not tested. *Open:* the smallest fix is to
start the deadline after the body is read. Left alone because giving a timed-out read back
is a recorded choice.

**S5. Low. A Generate here cap of 0 still let everyone generate once a day.** The limiter
in `worker/limits.js` admitted the first hit of each window whatever the limit was.
*Fixed:* a limit of 0 admits nothing, for every limiter. Test: "a cap of 0 means no free
generations at all".

**S6. Low. A deeply nested `changed` value gave a 500 on demand.** `validateChanged`
checked the keys of `changed` but not its values, which reach a recursive compare; a value
nested 20,000 deep overflowed the stack, and 500 such requests filled the day's server
error log so later real failures were not recorded. *Fixed:* a `changed` value nested deeper
than any shared field can be is a `400`. Tests: "a merge write's `changed` values are
bounded".

**S7. Low. Linking a project to a class assignment shows that assignment's title to
project members outside the class.** `worker/projects.js` `linkProject` writes the title
into the project's activity row. The shared-classes spec says the link shows class data
only to people in that class; the Stage 8 plan and `docs/DATA-MODEL.md` describe what the
code does. *Open:* the two documents disagree, so this needs George to say which is meant.

**S8. Low. A member the owner removed can rejoin at once with the join code they used
before**, while it has uses left and has not expired (`worker/invites.js` `joinByCode`,
`worker/leaving.js` `removeMember`). The spec allows "removed, then invited again" and says
nothing about codes. *Open:* clearing the code when a member is removed would close it, at
the cost of the owner issuing a new code for everyone else.

Not confirmed: whether a PNG sent to `/api/outline` as `application/octet-stream` runs
Cloudflare's paid image model (Workers AI is out of reach in tests); and there are no caps
on how many items, courses, sessions, decks or cards one account may hold, so one account
could in principle use up the D1 free plan's daily writes.

## Front end

**F1. High. A class's course sheet undid another editor's change on Save.**
`src/components/sheet/course-sheet.tsx` saved the whole draft it opened with. If another
editor moved the class to Tuesday while the sheet was open and this person changed only the
teacher, Save sent Monday back as this person's change and the Worker accepted it with no
conflict. *Fixed:* the sheet keeps the course as it was when opened, and Save writes onto
the course as stored now only the fields the draft changed. Tests:
`src/components/sheet/course-rebase.test.tsx`.

**F2. Medium. Editing a course again while its last save was uploading raised a false
conflict.** The draft carried the revision from when the sheet opened, so the second save
went out at the old revision, the Worker answered `409`, and the edit landed in Saved
copies. Same cause as F1. *Fixed* with F1: the revision comes from the stored row.

**F3. Medium. Using one toast's Undo or ✕ froze the other Undo toasts.** `src/data/toast.ts`
held the toasts still while focus was inside them and released the hold only on a blur;
removing the focused button's row sends none. The remaining toast never expired, so the
delete behind it was never made final until the tab was hidden. Shown in jsdom. *Fixed:*
taking a toast down lets go of the focus hold. Tests: `src/components/toaster.test.tsx`.

**F4. Medium. Merge paired unrelated items when titles were not in Latin letters.**
`src/data/merge.ts` `normTitle` kept only `a-z0-9`, so every Greek, Cyrillic, Arabic or CJK
title became empty and all of them matched: the merge sheet offered a sure pair between two
different items, and offered the wrong course. *Fixed:* titles compare by letters and
digits of any script, and an empty title matches nothing. Tests: `src/data/merge.test.ts`.

**F5. Medium. A new item saved "to the class for everyone" dropped the checklist and
status typed in the card.** `src/data/marks.ts` `addToClass` wrote `status: todo,
checklist: []` and made no mark. *Fixed:* the status, grade and steps go into your mark on
the new item. Tests: `src/data/marks.test.ts`. *Open, for a decision:* the card's Notes box
still becomes the class's notes, visible to every member.

**F6. Medium/low. An outline with no course code was filed under a different existing
course.** `src/core/importers/plan.ts` made a code from the name's first four letters (or
`NEW`) and then matched any course with that code: "Biology II" went under "Biology I".
*Fixed:* a course with no code matches yours only by name, and otherwise gets a made-up
code that is free (BIOL2). Tests: `test/importers.test.js`.

**F7. Low. Weekly calendar events whose name does not start with a Latin letter were all
skipped** on import (`codeToken` in `plan.ts`). *Fixed.* Tests: `test/importers.test.js`.

**F8. Low. A CSV weight written with a decimal comma was cut short** ("12,5" read as 12;
`src/core/importers/csv.ts`). *Fixed.* Test: `test/importers.test.js`.

**F9. Low. The score "needed" for a target was wrong when a course's weights pass 100.**
`src/core/grades.ts` `needed` assumed a total of 100 while the current grade divides by the
real total. *Fixed.* Test: `test/grades.test.js`.

**F10. Low. The office-hours "Next" dot could land on a weekly slot that had ended or not
started** (`nextMeeting` in `src/data/views.ts` ignored `date` and `recurUntil`). *Fixed.*
Tests: `src/data/views.test.ts`.

**F11. Low. A quote just added was not the one shown** (`src/data/actions.ts` assumed the
new quote is last; the list comes back in id order). *Fixed.* Test:
`src/data/quote-added.test.ts`.

Checked and sound: no `innerHTML` anywhere; links pass a scheme check twice, so a
`javascript:` link from another member is dropped; colours reach CSS only as `#rrggbb`;
peer text is rendered as text; the CSV export guards formula cells; local date handling
across DST; the grade maths apart from F9; the sync and store paths (item edits rebase onto
the stored row, uploads keep their order, a `409` goes to Saved copies); the importers'
quoting, folding and time handling.

Not confirmed, worth a look: the same stale-draft pattern as F1 in the inline task editor
(`task-row.tsx`: `assignees` from when it opened) and in `achievement-edit.ts` and
`session-edit.ts` (old revision); the backup leaves out a class's shared decks and cards;
a weighted lab or project can never be marked graded (those types have no such status).

## Worker data logic

Regression tests for the fixed ones: `test/audit-fixes.test.js`.

**L1. Medium. Converting a course into a class paid every finished item a second time, and
paid grade bonuses on personal grades.** `worker/buddy.js` keys a finish by scope
(`item:u:<id>`, then `item:c:<space>:<id>`), so an item that moves between scopes looks
freshly finished: 15 coins became 65 with nothing new done. Absorb and share-items change
the key the same way. *Open:* the fix (treat a finish as paid when any ledger row ends in
the same item id, and write off the grades a move carries) changes the game's rules, which
the Study Buddy plan owns.

**L2. Medium. Leaving a class with a copy re-paid up to five finishes and lowered XP**
(35 coins became 60, XP fell from 70 to 50). The same cause as L1, in the other direction.
*Open*, with L1.

**L3. Low/medium. The 240-minute day did not cap coins when sessions arrived out of start
order.** A session's coins are worked out from the day's fill order when read, and a paid
row never shrinks: a second device's earlier session arriving later gave 98 coins where
the day allows 50. *Open:* the fix (clamp so the day's `session:` rows sum to the cap) is a
rule change for the plan.

**L4. Medium. One study session with a far-future start made every Buddy read a 500.**
`validateStudySession` accepted `startedAt` up to `MAX_SAFE_INTEGER`, past what a date can
hold; one such row broke `GET /api/buddy`, the shop, claim and look until it was deleted.
*Fixed:* a session start or a card review time past the last moment a date can name is a
`400`. Test: "a date a clock cannot hold is refused". A row already stored that way would
still break the read; none is expected, but the live table is worth one query.

**L5. Medium. Extra AI uses bought today gave nothing while the 24-hour window still held
yesterday's extra uses** (the same defect as T4, found from the Worker's side: 120 coins
spent, no use). *Fixed* with T4.

**L6. Low. A use or read given back after its window ended was taken off the next
window** (`worker/study-ai.js` `giveBack`, `worker/limits.js` `giveBackOutline`): the next
window then shows one more use than it should. *Open:* small (have the claim return its
`reset_at` and give back only to that window); a follow-up, not done here.

**L7. Low. Friend search could not match a display name by its own capital non-ASCII
letter** ("Émilie" did not find "Émilie Roy": the query is lower-cased, SQLite's `LIKE`
folds ASCII only). *Fixed:* the pattern is the text as typed; only the exact-username
comparison is lower-cased. Test: "friend search finds a name by the letters it is written in".

**L8. Medium, for old v2 tabs only. A v2 pull from 0 with more than 100 rows below the
floor reset for ever**, never delivering rows past the first hundred (`syncPage` in
`worker/db.js`). v3 and v4 page the same data correctly. *Open:* the choice is between
retiring v2 with a "reload" answer and patching it.

**L9. Medium. The copy a class leaves behind kept a revived item's old grade category.**
`itemCopy` in `worker/leaving.js` updates every field of a revived row except `category`.
*Fixed.* Test: "the copy a class leaves behind takes the class's category on a revived item".

**L10. Low. An expired pending invite blocked other editors from inviting that person
again** for up to 90 days (`worker/invites.js`: "expired" is derived, the stored status
stays `pending`, and only the sender or the owner may overwrite a pending row). *Fixed:*
an invite that has expired, or whose sender's account is gone, can be replaced or withdrawn
by anyone who may invite. A live invite is still its sender's. Test: "an expired invite is
no longer in the way".

**L11. Low. Saving Buddy settings from another time zone paid the same streak day again**
under its new date (8 coins became 10). *Open:* a rule choice (pay only streak days later
than the newest paid one, or fix the zone once gameplay starts).

**L12. Low. An open assignment cost health for 13 days, not the window's 14**: the day
before the window, whose penalty falls on the window's first day, is not read. *Open:*
one line in `worker/buddy.js`, left for the plan with the other buddy rules.

**L13. Low. A lecture review whose title was edited was paid as a personal finish but
tallied later as a review**, so the day's five personal finishes became ten across two
reads. *Open:* which test is right (the id alone, or the id and the title) is the plan's.

**L14. Low. Someone taken out of a room for going quiet was under-credited when the host
paused and resumed afterwards** (15 minutes credited for 20 studied; `studyAt` in
`worker/rooms.js`, whose comment admits the limit). *Open:* needs the room's study time
stored with each `last_seen` write.

**L15. Low. Chat in a room that logged a session was never deleted**, though the schema
and DATA-MODEL say messages go 90 days after the room ends. *Fixed:* the nightly purge
deletes them; the room itself stays for its session. Test: "a room's chat goes 90 days
after the room ends, logged or not".

**L16. Low. Joining a room without an invite was not held to the 24 rows a room may
have** (30 friends joining and leaving left 31 rows). *Open:* the answer when a room is
full (replace the oldest left row, or refuse) is a choice.

Checked and sound: sync v3 and v4 paging across personal, class and project scopes with
writes between pages (every row delivered); revisions on upsert, revive and
purge-then-recreate; the shared-row and mark merges; every validator against its table's
CHECKs; the purge's ordering; account deletion (only intended references remain); leaving,
removal and deletion of classes and projects; the limits on spaces, members, tasks and
join-code uses, each checked inside the writing statement; the shop (no double spend, no
negative balance); room handover and chat pruning; friend request transitions.

Not confirmed: the purge may drop the `changes` row of a removed class item it keeps for
a mark, so a device resyncing from 0 would not get it until auto-keep reaches that person;
`decks.class_id` and `course_id` are not moved on leave or convert as items are (intended
behaviour is not written down); a multi-year swap range in a school calendar could run the
feed out of CPU; one digest is worked out from a person's first device's local day for all
their devices.

## What the review of the Study tab changed

These are improvements, not defects, made alongside the audit:

- **Timer tab.** The Ready card stretched to the height of the column beside it and centred
  its contents, so on a laptop Start focus was below the fold. It is now as tall as what it
  holds and stays in sight while the right column scrolls.
- **Study plan.** The plan was read-only text at the bottom of the tab. It is now the first
  card: today's topics per exam with boxes to tick, Study this to point the timer at the
  exam, and the days after. Today is fixed once for the day, so finishing today's topics
  ends the day's list instead of pulling tomorrow's forward
  (`src/core/study-today.ts`, tests in `test/study-today.test.js`).
- **Cards.** Each deck shows what is due and how well it is known, opens from its name, and
  can be reviewed on its own. New deck sits at the top instead of under the list. The end
  of a review says when cards come back.
- **Make cards with AI.** The form is in three numbered steps, takes dropped files, and
  says how much of long material each way reads: Generate here is sent about 12,000
  characters, and a long PDF was cut to that without a word. Saving offers Review now.
- **Phone.** The three Study tiles stacked and pushed the timer off the first screen; they
  are one row to swipe. A bottom bar gives Week, Month, Items and Study one tap each.

Suggestions not built, for the Study Buddy stages still to come: timing a card review so it
counts toward the streak and the daily goal; linking a generated deck to the exam it came
from, so the exam's card can show its due cards; an undo for a mis-pressed grade; and an
Undo for deleting a card or a deck, as every other personal delete has.
